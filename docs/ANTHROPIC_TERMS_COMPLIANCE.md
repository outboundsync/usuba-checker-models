# Anthropic terms compliance audit (2026-10-15)

Rule applied: no Claude, Sonnet, Opus or Haiku output may be used as training data, synthetic examples, labels, preference data, or as eval targets or gold answers. Scope: the working trees and the full git history of both repos (`usuba-checker-scripts`, `usuba-checker-models`), plus the Hugging Face staging folder. Method: case-insensitive search for claude, anthropic, sonnet, opus, haiku and `anthropic/` model ids across every tracked file and every historical blob; field-level scan of every staged dataset; review of every builder, judge and grader script for model ids.

## Result in one paragraph
No training row's answer, label or review text derives from Claude. Teacher text comes from Qwen3.5-397B-A17B (Apache-2.0), gate and spot-check calls use Qwen3.5-397B-A17B and gpt-oss-120b, and the other generation runs use open models (Qwen3.6-27B and stock Qwen peers). The only Anthropic use left in current files was (1) a Haiku judge that graded other models' answers, now replaced, (2) Claude as a competitor in score tables, and (3) six Claude-built plugins used as inputs in the private Dell key. Items 2 and 3 were decided by Harris on 2026-10-15 (see below).

## Findings
1. **Training data (hf-staging and repos): clean.** Every staged dataset was scanned field by field (`v3_r4_public`, `v3`, `clean`, `data`, `sources`). Hits for "claude" are only plugin content (plugins that talk about Claude Code, for example `mryll/claudebar`, README text, a commit subject "exclude Claude Code helper processes"), never an answer or label. r4 rows record their label models: `qwen/qwen3.5-397b-a17b` (finding-kind gate) and `openai/gpt-oss-120b` (spot check). The r4 LLM cache (private store) has no Anthropic model ids. `train/v3data/build_v3_data.py` has a filter (`BAD_WORDS`) that rejects any row text naming sonnet, claude, anthropic, deepseek, gemini, gpt or openai.
2. **History: an early Sonnet teacher existed and was removed.** Commits 2b5ca6e and 5ae9320 show the v2 distillation first used Sonnet 5.5 (`train/v2/distill/batches.py`, `anthropic_retry.sh`, `openrouter.py`, `gen_model_fixes.py`). The Sonnet outputs were quarantined outside the repos (`quarantine-sonnet/` in the private store) and never trained on; the proprietary-model fix rows were dropped. The old runner scripts (code only, no outputs) were in history until the rewrite described in decision 6. History also holds `runs/smoke-2026-10-11/*claude*.log` and `scores_claude-*.json` (pass/fail score tables and cost lines, no model text). No raw Claude completions exist in either repo's history; searches for answer directories, raw jsonl and cache files in history found none.
3. **Haiku as judge (the gray area).** `eval/dellkey/reason_grade.py` defaulted to `anthropic/claude-haiku-5.5` to decide whether a model's finding names the real cause (right-reason). It graded our models' and open peers' outputs against the hardware key; Claude output was not a label, but Haiku's verdicts were the reported metric. Used by: `docs/v3prep/COMMANDS.md`, `docs/v3prep/exam_v3prompt/or_run_v3.sh`, and the right-reason numbers in `docs/TRAINING_PLAN.md` (v1, v2 and v3 exam tables) and `docs/post/draft.md`.
4. **Claude as a competitor in score tables.** README (headline table) and `docs/TRAINING_PLAN.md`: Claude Sonnet 5.5 with its own skill prompt, HANCORE holdout, scores only (`eval/hancore_holdout/results/frontier-sonnet-5.5.json`, no raw output). Also Sonnet and Opus pass counts in `docs/post/*`, `docs/LEGACY_README.md`, `reviews/context_pack.md`, `runs/uplift/*` (builder runs with Checker feedback: pass/fail, cost, human hand-check notes; the answers themselves are not in the repos), `runs/rescore404/*`, scripts `functest/results.json` and `rescore.log` (per-task pass/fail with check categories, no model text). Gold answers in these evaluations come from HANCORE reviews, real upstream fixes, hardware runs and the Checker, not from Claude.
5. **Claude-built plugins as eval inputs.** The private Dell key contains 6 rows whose plugin code was generated by Claude Opus 5.5 (`b3.opus55.*`; the same key also has GPT-5.6 and Qwen builds). The labels are hardware observations, not Claude text, but Claude output is the thing being reviewed. The key is not published; two of the six have entries in `eval/dellkey/reason_rubric.json` (`b3.opus55.acme-dropbox`, `b3.opus55.acme-power`, a short cause summary: "no barWidget entry point").
6. **Authorship of "house" training plugins.** 51 rows in the staged `data/train.jsonl` come from `kenhara/*` plugins (house origin). I cannot tell from the repo which tools wrote that code. Community plugins in the training pool may also be AI-assisted (some ship CLAUDE.md or `.claude/`); that cannot be audited from here.
7. **Counts of tooling references.** Remaining matches in `dell-ref/` (upstream Omarchy files such as the agents plugin and a Claude theme) and in rule code (HC16 detects shipped agent control files such as `CLAUDE.md`) are third-party content or detection patterns, not model use.

## Decisions by Harris (2026-10-15) and what was done
1. **Sonnet 5.5 baseline: keep as a score table only**, labelled as a third-party comparison (README headline table, `docs/TRAINING_PLAN.md`, `docs/post/draft.md`). No Claude output is used anywhere in the project; the repos contain only pass/fail and score numbers for Claude.
2. **Claude-built plugins excluded from the Dell key.** The six `b3.opus55.*` plugins (Opus 5.5 builds) are excluded from the key and every eval table. Only 4 of the 6 were decided rows (2 BROKEN, 2 WORKS; the other 2 were UNSURE and never counted), so the decided key goes from 90 to **86 rows (31 broken, 55 works)**, not 84. `eval/dellkey/reason_grade.py` and `eval/hancore_holdout/run_eval.py --set dellkey` skip ids starting `b3.opus55.`; the two rubric entries were removed from `eval/dellkey/reason_rubric.json`; `table.py` now reads the broken count from the results. The 13 systems whose raw answers exist were regraded on the 86-row key (open judge gpt-oss-120b, plus the regex rubric); results are in `docs/TRAINING_PLAN.md` and `eval/dellkey_open_judge/summary.json`. Stock Qwen3.5 9B on prompt v3: 9/31 right-reason (open judge), 13/31 (regex). A repeat of the judge run moved one system by one catch, so judge counts carry about plus or minus 1. The excluded plugins remain on the training exclusion list (they were never training data). The Dell key itself is not published.
3. **Haiku-judged numbers that cannot be regraded** (no raw answers on the box: Usuba v1, Sonnet, most v1/v2 peers, the bf16 diagnosis) are relabelled "Haiku-judged, historical" in `docs/TRAINING_PLAN.md` and `docs/post/draft.md`, with the note that they are on the old 90-row key and not comparable to the 86-row numbers. The README carries no judge-based number.
4. **Open judge** (`reason_grade.py`): default `openai/gpt-oss-120b`, optional `qwen/qwen3.5-397b-a17b`; Anthropic or Claude judges are refused; `--suffix` keeps a second judge's output separate. Historical Haiku mentions in `docs/v3prep/*` are labelled superseded.
5. **Unaudited authorship.** I have not audited who or what wrote the `kenhara/*` "house" rows (51 rows in the staged `data/train.jsonl`) or the community plugins in the training pool that ship `CLAUDE.md` or `.claude/` files (which suggests AI-assisted code). No rows were removed on that basis; this stays a known gap.
6. **History rewrite (private repos only, Harris approved 2026-10-15).** The early Sonnet runner scripts and Claude score logs were path-filtered out of the history of `usuba-checker-models`: `train/v2/distill/{anthropic_retry.sh,batches.py,openrouter.py,run.sh}`, `train/v2/gen_model_fixes.py`, and `runs/smoke-2026-10-11/{big,or,rr}_claude-*.log`, `runs/smoke-2026-10-11/scores_claude-*.json`. All commit hashes changed and the rewritten `main` was force-pushed with `--force-with-lease` to the two private repos only. Score tables for Claude that remain in current files (README, TRAINING_PLAN, `runs/uplift`, `runs/rescore404`, scripts `functest/results.json`) are kept as third-party comparisons per decision 1.

## Changes in the first pass (open judge)
- `eval/dellkey/reason_grade.py`: the judge is now an open-weights model. Default `openai/gpt-oss-120b`; `qwen/qwen3.5-397b-a17b` also supported (`--judge-model`, slower). Any `anthropic/` or `claude` model id is refused with an error; non-open ids need `--allow-closed-judge`. New `--suffix` keeps a second judge's output next to the first. Calls use OpenRouter zero data retention, temperature 0, reasoning effort low, 4000 max tokens. The regex rubric (`det`) stays as an independent metric.
- Regrade: the prompt-v3 Dell exam (8 systems) and the five v2 systems whose raw answers were on the box (13 gradings) were rerun with gpt-oss-120b (total about $0.02). Results, next to the original Haiku counts and the regex counts, are in `eval/dellkey_open_judge/summary.json`. Haiku and gpt-oss-120b differ by at most 1 catch per system, except Usuba v2 (Q4_K_M), which drops from 2 to 0 (for example stock Qwen3.5 9B 10 vs 9, Ministral 14B 12 vs 11, Gemma 4 26B v2 14 vs 13); judge-versus-regex agreement is 0.69 to 0.95. The Haiku figures in `docs/TRAINING_PLAN.md` are marked superseded and the open-judge numbers added; the gate-(c) bar for stock Qwen3.5 9B becomes 9/31 on the 86-row key (see decision 2).
- `docs/v3prep/COMMANDS.md`, `docs/v3prep/exam_v3prompt/or_run_v3.sh`: judge references now point to the open judge, with the original Haiku run labelled as superseded.
